# 统一元数据平台架构分析：跨会话交接说明

> 用途：在后续会话取得真实代码仓后，基于代码证据重新分析并绘制总体视图和 4+1 架构视图。
>
> 重要结论：当前 PlantUML 仅是需求层概念草图，不能作为最终架构设计或代码现状说明。

## 1. 当前诉求与已确认事实

### 1.1 系统目标

建设一套统一元数据存储与检索系统：

- 对外兼容 Gravitino、Iceberg 等生态。
- 对内兼容用户自定义的内部数据结构。
- 底层支持 StarRocks、Iceberg、OpenSearch 等数据源，并保留扩展能力。
- 面向亿级元数据提供秒级检索能力。
- 最终需要总体架构视图及 4+1 架构视图。

### 1.2 已确认的结构性设计

1. **外部生态入口**
   - 系统先定义统一抽象类。
   - Gravitino、Iceberg 等不同生态通过该抽象类实现各自入口。
   - 外部协议对象在入口层被转换或包装为统一内部结构。

2. **OpenSearch 混合索引**
   - 处理后的统一内部结构根据查询粒度和更新粒度分类写入 OpenSearch。
   - 索引规划包括：`catalog`、`schema`、`dataset`、`table`、`tags`、`tags-relation`。
   - 使用动态模板支持产品自定义查询 Key。
   - 限制 Mapping Key 数量，避免索引爆炸。

3. **底层数据源下放**
   - 处理后的统一内部结构同时进入底层数据源写入路径。
   - 根据数据源类型，通过工厂类选择或创建具体数据源实现。
   - 当前目标数据源包括 StarRocks、Iceberg、OpenSearch，并应允许继续扩展。

### 1.3 尚未确认、不得直接假设的内容

- 统一入口抽象类、统一内部结构、数据源工厂的真实类名和包名。
- 抽象类使用 Template Method、Strategy、Adapter 或其他实现模式的具体方式。
- 工厂是简单工厂、工厂方法、抽象工厂，还是结合注册表/依赖注入实现。
- 外部协议入口与内部模型转换发生在哪个模块、哪个调用阶段。
- OpenSearch 索引的真实名称、alias、template、mapping、routing、shard 和 refresh 配置。
- 六类索引是否全部已实现，还是目标方案。
- 标签内容与标签关系的真实存储模型。
- StarRocks、Iceberg、OpenSearch 是并行写入、按租户选一、按对象类型选择，还是承担不同职责。
- 事实源、索引源和历史源的权威关系。
- 写入是否经过 MQ、CDC、Outbox、异步 Worker 或定时任务。
- 查询路径是否回源、如何聚合、如何做权限过滤和深分页。
- 一致性、幂等、版本控制、失败重试和补偿机制。
- 实际性能指标：数据量分布、QPS、写吞吐、P95/P99、索引延迟和可用性目标。

当前图中出现的 `AbstractMetadataEntry`、`CanonicalMetadata`、`DataSourceFactory`、`AbstractDataSource` 等名称均为占位名称。拿到代码后必须替换为真实名称，或明确标注为建议新增的设计元素。

## 3. 下一轮强制分析流程

### 3.1 仓库与模块盘点

1. 读取仓库中的 `AGENTS.md`、README、构建文件和目录结构。
2. 确认语言、框架、模块边界、启动入口和部署单元。
3. 区分生产代码、测试代码、示例代码、生成代码和废弃代码。
4. 记录分析所基于的仓库 URL、分支和 commit SHA。

### 3.2 外部接口适配链路

从 Gravitino、Iceberg 及其他外部入口反向和正向追踪：

1. Controller、Resource、Service、Catalog 或 RPC 入口。
2. 统一抽象类及其继承实现。
3. 抽象方法、默认方法、公共逻辑和子类差异逻辑。
4. 外部 DTO/协议对象到内部模型的 Mapper、Converter、Assembler。
5. 异常转换、鉴权、租户上下文、事务边界和版本兼容。

必须回答：

- 谁是统一入口抽象？
- 哪些类继承或实现它？
- 公共逻辑实际位于哪里？
- 外部协议对象在哪一步成为统一内部结构？
- 新增一种生态需要修改哪些代码和配置？

### 3.3 内部模型与索引链路

从统一内部结构追踪至 OpenSearch：

1. 内部核心对象、继承结构、组合关系和版本字段。
2. 对象类型到索引类型的分类器或路由器。
3. Index Document Builder、Mapper、Template、Repository/Client。
4. `catalog`、`schema`、`dataset`、`table`、`tags`、`tags-relation` 的真实实现状态。
5. 动态模板、自定义 Key、字段类型冲突和 Mapping Key 上限。
6. Bulk、Upsert、Delete、alias 切换、重建和回填流程。
7. 查询入口、查询 DSL、分页、排序、聚合、标签关联和回源流程。

必须区分：

- **代码中已经存在的索引结构**。
- **配置中声明但代码尚未使用的结构**。
- **本次方案希望新增的结构**。

### 3.4 数据源工厂与下放链路

从统一内部结构追踪至底层数据源：

1. 工厂类、工厂接口、注册表或依赖注入配置。
2. 数据源类型枚举、配置对象和创建条件。
3. StarRocks、Iceberg、OpenSearch 等具体实现类。
4. 工厂创建后的调用方式、连接生命周期和资源释放。
5. 单写、双写、多写、按类型路由或按租户路由规则。
6. 事务、一致性、失败重试、补偿、幂等和降级机制。

必须回答：

- 工厂根据什么字段选择数据源？
- 工厂返回什么公共类型？
- 数据源实现共享哪些能力，差异能力如何表达？
- 新增数据源需要修改工厂源码，还是只需注册配置？
- OpenSearch 在系统中是搜索索引、业务数据源，还是同时承担两种角色？

### 3.5 运行与部署证据

检查配置和部署文件，确认：

- 实际服务进程和部署单元。
- 同步调用、异步任务、线程池、队列和定时任务。
- 数据库、对象存储、OpenSearch、StarRocks、Iceberg 及中间件连接。
- 高可用、扩缩容、分片、副本和故障恢复配置。
- Metrics、Logs、Traces、告警和健康检查。

## 5. 证据与绘图规则

### 5.1 代码证据要求

- 每个关键节点必须能映射到代码模块、类、配置或明确的规划需求。
- 每条关键箭头必须能映射到调用、依赖、继承、创建、消息或数据流证据。
- 图中若使用概念名代替多个真实类，必须使用 `<<concept>>` 标注，并在证据矩阵列出其组成。
- 规划中的组件使用 `<<planned>>`，不得与已实现组件混画为同一状态。
- 推断关系使用虚线，并在文档中列出待确认问题。

### 5.2 绘图质量要求

- 总体视图先宏观后局部，不在一张图同时塞入所有类、索引字段和部署节点。
- 逻辑视图按真实职责分层，层与层之间只保留主调用或数据流。
- 继承箭头、工厂创建箭头、业务调用箭头和数据流箭头必须使用不同标签说明。
- OpenSearch 索引路径与底层数据源下放路径必须明确区分。
- 若 OpenSearch 同时承担两种角色，必须分别命名并说明，而不是绘制成一个含义不清的节点。
- SVG 必须经过人工视觉检查，确保文字、连线、分组和层级清晰。

### 5.3 验收标准

下一轮产物至少满足：

1. 总体图能够在不阅读代码的情况下解释系统边界和两条核心数据路径。
2. 逻辑图中的真实类和模块可以在代码仓中直接定位。
3. 抽象入口继承体系与工厂创建体系均与代码一致。
4. 已实现、规划和推断内容清晰区分。
5. 索引分类与主要业务查询场景之间存在明确对应关系。
6. 图、证据矩阵和文字说明不存在互相矛盾。
