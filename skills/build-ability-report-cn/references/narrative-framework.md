# 叙事框架

## 1. 汇报要证明什么

领导需要看到的不是“做过多少需求”，而是个人处理问题的方式发生了什么变化：

1. 能否把需求做稳，并在开发前提高设计与验证质量。
2. 能否超越表象，找到根因并形成更优解。
3. 能否把一次解决沉淀为方法，减少后续重复投入。
4. 能否在事实不足、方案未定和依赖复杂时创造推进条件。

将职位目标留在幕后。即使汇报服务于晋升，也应让案例自然证明能力，而不是反复声明“具备负责人能力”。

## 2. 从原始案例提炼能力

对每个案例回答四个问题：

- **难度来自哪里**：规模、性能、模型差异、跨系统一致性、上下游依赖还是信息不完整？
- **个人判断是什么**：发现了什么被忽略的矛盾、边界或风险？
- **关键动作是什么**：哪些动作不是普通需求执行者自然会做的？
- **价值如何延续**：结果只解决当次问题，还是形成结构、流程、Skill、基线或协作机制？

再按能力半径归组：

- **把事情做好**：设计前置、边界补齐、验证充分、稳定交付。
- **把问题想深**：定位根因、重构结构、优化性能、沉淀方法。
- **把复杂事情推动成功**：求证事实、拆分依赖、组织并行、推动闭环。

这些是分析维度，不是默认的可见标题。

## 3. 建立递进而非并列

弱结构是三个互不相关的能力清单。强结构应解释能力半径如何扩大：

> 从保证自己的交付质量，到改变问题的解决方式，再到为多人协作创造确定性。

阶段可以时间重叠。个人简介页不要伪造严格先后，可以使用：

- 起点明确、后续重叠的能力泳道。
- 三条逐渐延伸的能力带。
- 以项目节点为锚点、能力线并行上升的轨迹。

## 4. 提炼章节标题

章节标题采用两层结构：

- **成长阶段词**：简短、有画面感，如“初试羽翼”“独当一面”“并肩作战”。
- **观点标题**：直接概括该页的能力变化，如“设计先行：把关键问题解决在开发前”。

不要使用：

- 完成层、优化层、协作层。
- 技术判断力、Owner 意识、组织协调能力。
- 个人能力展示、证明重点、能力主线。

这些词可以用于内部分析，但不能替代案例观点。

## 5. 提炼封面主题

先完成主体页，再从共同方向抽取主题。主题应满足：

- 8–12 个汉字，适合两行或一行排版。
- 足够抽象，但能解释每个主体页。
- 不直接写职位目标、部门名称或“能力汇报”。
- 避免任何年度总结都能使用的空泛口号。

常见主题方向：

- **深度与半径**：向深扎根，向外生长。
- **积累与行动**：深耕笃行，进而有为。
- **持续精进**：步步精进，行稳致远。
- **探索与拓展**：向深求索，向远而行。

检查方法：分别用一句话解释主题如何对应每个主体页。若只能解释一页，重新提炼。

## 6. 总结与展望

总结页不要再次复述案例过程。每栏写：

- 已形成的能力变化。
- 仍需提升的一个具体方向。
- 下一步如何在现有基础上扩大作用范围。

展望避免“继续努力、持续学习、提升能力”。改为可观察的方向，例如：跨域方案取舍、方法抽象通用性、风险节奏预判、共识建立效率。
