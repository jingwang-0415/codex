# 文案与证据

## 1. 单页文案骨架

按以下顺序写主体案例页：

1. **观点**：一句话说明该页想证明的工作方式。
2. **背景与目标**：交代业务对象、系统范围、关键约束和目标规格。
3. **挑战**：只保留决定方案难度的 1–3 个矛盾。
4. **我的做法**：写判断和动作链，不写通用职责。
5. **效果**：用最适合该问题的证据表达。
6. **结论**：提炼可迁移的观点，不复述动作和数字。

背景不应因压缩而失去可读性。先删除重复信息，再缩短句子，不要只砍关键词。

## 2. 写“我的做法”

使用“观察 → 判断 → 选择 → 验证 → 调整”的动作链：

> 结合真实查询路径复盘点边关系，判断通用扩展设计导致多跳路径膨胀；在保持业务结果不变的前提下重构图模型，并用同等数据集验证查询变化。

避免：

- 积极沟通、主动推进、深入分析、充分考虑。
- 负责方案设计、完成开发测试、保障按期交付。
- 具备技术判断力、体现 Owner 意识。

这些词缺少可验证动作。

## 3. 为不同问题选择不同证据

| 问题类型 | 推荐效果表达 |
| --- | --- |
| 架构边界 | 收敛前后图、模型映射图、职责边界图 |
| 数据一致性 | 责任边界、故障控制矩阵、恢复路径 |
| 查询性能 | 同环境前后指标、P95/P99、吞吐或跳数对比 |
| 需求设计 | 提前识别的边界问题、评审轮次或返工减少 |
| 方法沉淀 | 覆盖问题类型、复用范围、平均定位时间变化 |
| 复杂协作 | 风险如何被验证、等待如何被解耦、最终节点是否达成 |

不要让三个完全不同的问题都使用“挑战—动作—结果”三张同款卡片；内容结构可以一致，证据形态必须贴合问题。

## 4. 指标规则

- 只将同等数据量、并发、硬件和查询条件下的对比写为项目提升。
- 明确区分“优化前”“优化后”“行业参考”“待实测”。
- 不从无法支撑的多项数字推导“综合提升 X 倍”。
- 精确查询若前后无差异，明确写“保持稳定”，不要伪造改善。
- 没有完整前后数据时，写已验证的能力边界，不写百分比。
- 计算提升比例时使用：`(优化前耗时 - 优化后耗时) / 优化前耗时`。

## 5. 融合 AI

AI 必须嵌入真实解决过程：

- 需求设计：从业务流程、权限、状态、异常、一致性和依赖等维度反向提问。
- 开发验证：生成重复性数据、脚本和校验逻辑，人工负责场景与判定标准。
- 疑难定位：把专家排查路径沉淀为 Skill 或 MCP 流程，并通过真实问题试点。
- 方法沉淀：整理复盘、问题模式和标准定位步骤。

推荐写法：

> 在统一模型推演中，将 AI 生成的边界问题清单纳入设计自检，补齐异常场景后再进入评审。

避免单独悬浮：

> AI 反向审查 6 类维度，提前识别 5 个问题。

数字可以保留，但应出现在对应动作或结果中，而不是变成与案例割裂的宣传句。

## 6. 结论升华

结论应回答“这种工作方式为什么值得复用”。

案例总结：

> 图结构优化减少无效路径，定位 Skill 减少重复咨询。

更高一层的观点：

> 越能从表象追到根因、把经验沉淀为方法，后续解决同类问题的重复投入越少，一次实践产生的价值越持久。

协作案例可提炼为：

> 用实测收敛判断，用解耦创造并行，让复杂协作从等待转向推进。

保持“一句短观点 + 一句解释”的格式。短观点左对齐，解释句在统一宽度内居中或按模板统一对齐。
