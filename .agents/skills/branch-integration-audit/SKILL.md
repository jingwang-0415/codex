# 分支漏合入检查

目标是核实旧分支中需要保留的行为是否仍存在于新分支。提交可达或 patch-id 相同只是线索；合并之后的 revert、冲突解决和后续改动也可能丢失行为。不得仅凭 `git log`、`git cherry` 或文件存在就宣布完整合入。

## 1. 明确范围并固定证据

- 明确仓库、旧分支（来源）、新分支（目标），以及用户指定的路径、发布基线和例外。如果方向未给出且无法从上下文确定，先询问；不要凭分支名推断新旧。
- 默认检查旧分支当前有效的全部行为，包括共同祖先中已有而被新分支删除的代码。历史上已在旧分支撤销的修改不自动视为必须迁移。
- 查看适用的 AGENTS.md 和工作区状态。默认只读，不切换分支、不合并、不 cherry-pick、不 reset、不修改源码，也不创建 worktree。运行测试需要临时文件时放在仓库外。
- 本地引用可能落后于远端。按需要 fetch 用户指定的远端/分支（不自动 prune），记录是否成功；失败后仅能报告本地快照结论。不得因此要求用户提供已有代理可用的 GitHub token。
- 固定两个完整提交 SHA，后续始终使用 SHA，记录脏工作区、浅克隆、子模块、LFS 和缺失对象。工作区未提交内容不包含在分支快照中。

运行随 skill 提供的收集器（仅依赖 Python 3.10+ 和 Git；替换实际路径和分支名）：

```bash
audit_dir=$(mktemp -d /tmp/branch-audit.XXXXXX)
python /path/to/branch-integration-audit/scripts/collect.py \
  --repo /path/to/repo --old origin/release-old --new origin/release-new \
  --out "$audit_dir/evidence"
```

收集器不会联网或改动被检仓库；输出必须为仓库外的新目录。检查退出码和 `summary.json`，收集错误不可当作“无差异”。输出包含源码，应按原仓库访问权限保管，不向外部服务上传。

## 2. 两条独立检查路径

**提交路径：** 阅读 `summary.json` 中旧分支独有提交、父提交和 `cherry.txt`。`+` 是待检查候选，`-` 表示存在补丁等价的普通提交。逐项追踪其变更目的、受影响函数、配置和测试；squash、拆分、重写会让 `+` 误报。为每个候选记录对应目标实现或遗漏证据。

**最终状态路径：** 完整审阅 `old-to-new.patch` 和文件状态列表，特别检查删除、重命名、模式变化、二进制文件、配置默认值、注册/调用入口、依赖、迁移脚本和测试。该方向的删除表示旧分支存在而新分支缺少。即使旧分支是新分支祖先、没有独有提交，也必须执行此路径，防止合并后回退和合并冲突丢代码。

共同祖先到两个 tip 的补丁用于解释各自演化；不能用 `old...new` 的单侧 diff 替代最终状态比较。多个 merge base 时保留全部基线，不任意选一个形成肯定结论；没有共同祖先时使用最终树比较并明确历史映射受限。浅历史需在授权网络范围内补全后重新收集；无法补全时结论为检查不完整。

旧分支独有的 merge commit 必须单独审查。用 `git show --remerge-diff <sha>`（Git 支持时）或对各父提交的 diff 检查冲突解决；不能依赖默认隐藏 merge patch 的日志。目标侧的 merge/revert 也要通过按路径的历史和最终代码追踪。

## 3. 行为与覆盖核对

按功能单元建立台账：旧分支的入口、实现、调用方、配置/权限/错误路径、边界处理和测试，在目标中逐项定位。使用 `git show <sha>:<path>`、`git grep -n -e <pattern> <sha> -- <path>` 和固定 SHA 的历史，不把当前工作区当作目标分支。

逐项分类，区分事实与推断：

| 分类 | 所需证据 |
| --- | --- |
| 已承接 | 对应目标代码路径与行为证据，确认后续没有撤销 |
| 等价改写 | 新旧实现映射及针对关键行为的测试/推导 |
| 经确认不迁移 | 用户明确范围或可追溯的设计/变更依据 |
| 疑似遗漏 | 旧行为有效，目标未找到完整实现；列出搜索范围与缺口 |
| 已证实遗漏 | 可复现的行为差异、缺少调用/分支等直接证据，且属于必须保留的范围 |
| 无法判断 | 缺少历史、依赖、业务意图或运行条件；列出具体缺口 |

不要把“目标删了代码”自动当作错误，也不要猜测这是刻意删除。未确认的语义变化保留为待确认项。

运行与变化相关的现有测试；必要时用仓库外的临时复现验证同样输入在新旧版本的行为。保留两边各自的依赖与配置，记录命令、退出码和实际执行用例。测试环境失败不等于代码遗漏，零用例或跳过也不等于通过。不要修改测试来消除失败。构建或运行不受信任分支前检查脚本行为与所需权限。

子模块 gitlink 变化需要进入对应仓库继续审查；仅有 LFS 指针、二进制 diff 标记不能证明内容等价。未取得实际对象时报告未覆盖。

## 4. 报告与结论

按照 [报告模板](references/report-template.md) 输出完整报告。先给有证据支持的结论，再列高影响缺口、映射台账和验证结果。每项引用固定 SHA、路径、函数/行号及相关提交，说明影响和建议迁移内容；默认不执行修复。

检查量大时分批，但必须维护总量、已检查量、未检查清单；不能把抽样结果写成全量结论。所有候选和最终状态差异都要有去向，测试通过不能代替覆盖台账。

只有范围内无未解释差异、无疑似遗漏或无法判断项，且所需验证完成，才可以说“在所列范围和验证条件下未发现漏合入”。不要承诺绝对不存在遗漏。有未覆盖项时说“检查不完整”，并给出完成检查所需的具体信息。
